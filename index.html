CONCEPTOS

Git y GitHub no son lo mismo

GIT

Control de versiones

Programa que guarda la historia de tus archivos en tu computadora. Te deja volver atrás, comparar cambios y trabajar en ramas.

GITHUB

Plataforma en la nube

Sitio web que aloja repositorios de Git y agrega colaboración: issues, pull requests y revisiones.

Git trabaja en tu máquina. GitHub es donde lo compartes con otros.

PASO 1

Instalar y configurar tu identidad

Git necesita saber quién hace cada cambio. Ese nombre y correo aparecen en cada commit.

Terminal
git --version
git config --global user.name "Tu Nombre"
git config --global user.email "tu@correo.com"
git config --global --list
Agentes IA
Revisa si git está instalado. Si lo está, configura mi nombre
y correo globales para git con los datos que te doy a
continuación. Antes de escribir, muéstrame la configuración
que vas a aplicar.

Qué esperar: git --version muestra la versión instalada. --list muestra tu nombre y correo.

PASO 2

Crear un proyecto con repositorio

Un repositorio es una carpeta que Git vigila. git init la convierte en repositorio.

Terminal
mkdir mi-proyecto
cd mi-proyecto
git init
git status
Agentes IA
Crea una carpeta llamada mi-proyecto en este directorio,
inicialízala como repositorio de git y muéstrame el estado.

Qué esperar: aparece la carpeta .git (oculta) y git status dice que estás en la rama main sin commits todavía.

PASO 3

Primer cambio: status, add y commit

Editasgit statusgit addgit commit
Terminal
echo # Mi proyecto > README.md
git status
git add README.md
git commit -m "docs: add README"
git log --oneline
Agentes IA
Crea un README.md con el título "Mi proyecto" y una
descripción de una línea. Muéstrame git status, agrega el
archivo al área de preparación y haz un commit con el mensaje
"docs: add README".

Qué esperar: git status muestra el archivo en rojo (sin preparar). Después de add pasa a verde. git log muestra tu commit.

Diferencia: git add . prepara todos los cambios. Revisa git status antes para no subir archivos por error.

PASO 4

Mensajes de commit claros

Usa el formato tipo: descripción corta, en imperativo. Así cualquiera entiende la historia.

feat

Funcionalidad nueva: feat: add login form

fix

Corrección de un error: fix: handle empty email

docs

Solo documentación: docs: explain install steps

PASO 5

Ignorar archivos con .gitignore

Hay archivos que no deben entrar al repositorio: dependencias, secretos y resultados de compilación.

Terminal
echo node_modules/ > .gitignore
echo .env >> .gitignore
git add .gitignore
git commit -m "chore: add gitignore"
Agentes IA
Crea un .gitignore adecuado para mi proyecto (ignora
dependencias, archivos de entorno y compilados). Haz commit
con el mensaje "chore: add gitignore".

Qué esperar: git status ya no muestra .env ni node_modules/, aunque existan.

PASO 6

Trabajar en ramas

Una rama es una línea de trabajo aislada. main queda estable y cada tarea vive en su propia rama.

Terminal
git branch
git switch -c feature/login
git add .
git commit -m "feat: add login form"
git switch main
git merge feature/login
git branch -d feature/login
Agentes IA
Crea una rama llamada feature/login a partir de main,
haz los cambios necesarios para el formulario de login y
haz commit. Después vuelve a main, haz merge de la rama y
borra la rama local.

Windows y versiones antiguas: git switch -c es equivalente a git checkout -b. Ambas crean y cambian de rama.

PASO 7

Subir tu repositorio a GitHub

Crea un repositorio vacío en GitHub (sin README ni .gitignore), copia su URL y conéctalo.

Terminal
git remote add origin https://github.com/TU-USUARIO/TU-REPO.git
git push -u origin main
Agentes IA
Crea un repositorio público llamado TU-REPO en mi cuenta
de GitHub (sin README) y conecta este proyecto como origin.
Luego sube la rama main.

Qué esperar: al refrescar la página del repositorio en GitHub aparecen tus archivos y tus commits.

Autenticación: la primera vez, Git te pedirá iniciar sesión. Con GitHub CLI: gh auth login.

PASO 8

Crear issues

Un issue describe un problema, una mejora o una tarea. Título claro, contexto y criterio de terminado.

Terminal
gh issue create --title "Login falla con correo vacío" --body "Al enviar el formulario sin correo la app se cierra. Esperado: mensaje de error."
gh issue list
Agentes IA
Crea un issue en este repositorio con el título "Login falla
con correo vacío" y una descripción con pasos para reproducir,
resultado esperado y resultado actual.

Requisito: gh (GitHub CLI) instalado y autenticado con gh auth login.

PASO 9

Pull requests

Un pull request (PR) propone fusionar tu rama a main para que otra persona la revise.

RamaCommitPushPRRevisiónMerge
Terminal
git push -u origin feature/login
gh pr create --fill
gh pr view --web
Agentes IA
Sube la rama feature/login y abre un pull request hacia
main. En la descripción pon "Closes #1" para vincular el
issue y resume los cambios en 3 viñetas.

Tip: Closes #N en la descripción cierra el issue N automáticamente al hacer merge.

PASO 10

Mantener las ramas al día

Antes de empezar, trae los cambios del equipo. Mantén ramas cortas y bórralas cuando se fusionan.

Terminal
git switch main
git pull
git fetch --prune
git branch -a
git branch -d feature/login
Agentes IA
Actualiza main desde origin, limpia las referencias a ramas
que ya no existen en el remoto y dime qué ramas locales
puedo borrar porque ya están fusionadas. No las borres sin
confirmarme.

Qué esperar: git branch -a muestra las locales y las remotas (remotes/origin/...).

PASO 11

Trabajar en equipo

Clona el repositorio, trabaja en tu rama y sincroniza con frecuencia para evitar sorpresas.

Terminal
git clone https://github.com/TU-USUARIO/TU-REPO.git
cd TU-REPO
git switch -c feature/mi-tarea
git push -u origin feature/mi-tarea

# Si el push es rechazado, trae los cambios primero:
git pull --rebase
Agentes IA
Clona https://github.com/TU-USUARIO/TU-REPO.git, crea la
rama feature/mi-tarea y súbela a origin. Si el push falla
porque el remoto tiene cambios, explícame la causa antes de
hacer pull --rebase.

Regla de equipo: nunca hagas push directo a main si el equipo usa PRs. Trabaja en una rama.

PASO 12

Resolver un conflicto

Un conflicto aparece cuando dos personas cambian la misma línea. Git marca el lugar y tú decides qué queda.

<<<<<<< HEAD
const title = "Login";
=======
const title = "Iniciar sesión";
>>>>>>> feature/login
Terminal
git pull
# Edita el archivo: deja una versión y borra las marcas <<<, ===, >>>
git add archivo-en-conflicto.js
git commit -m "fix: resolve title conflict"
Agentes IA
Hay un conflicto de merge en archivo-en-conflicto.js.
Muéstrame ambas versiones, explícame la diferencia y
propón una resolución. Espera mi confirmación antes de
hacer add y commit.

Importante: borra siempre las marcas <<<<<<<, ======= y >>>>>>> antes de hacer commit.

PASO 13

El README: la puerta de entrada

El README es lo primero que lee alguien que llega a tu repositorio. Debe responder: qué es, cómo instalarlo y cómo usarlo.

01

Título

Nombre y una línea de descripción.

02

Instalación

Comandos exactos para empezar.

03

Uso

Un ejemplo que funcione.

04

Contribuir

Ramas, PRs e issues.

Terminal
git add README.md
git commit -m "docs: improve README"
git push
Agentes IA
Lee el código de este proyecto y escribe un README.md con:
título, descripción, requisitos, instalación, uso con un
ejemplo y cómo contribuir (ramas, issues y PRs). Haz commit.
